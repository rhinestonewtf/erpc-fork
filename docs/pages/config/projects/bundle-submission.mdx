# Bundle submission

On a public mempool, a transaction that reverts still lands and still pays gas, and a
pending one can be front-run or copied. Bundle submission turns every
`eth_sendRawTransaction` on a network into signed `eth_sendBundle` requests to relays you
choose, such as Flashbots, for the next few blocks, and keeps the transaction submitted
block after block until it lands. Builders only include a bundle whose transaction
succeeds. Callers keep calling `eth_sendRawTransaction` and still get the transaction hash
back.

**What you get**

- No path to the public mempool: retries, hedges and failover can't reach the network's ordinary upstreams
- Reverting transactions don't land, so they cost nothing
- Mempool-like retention: an accepted transaction stays submitted until it is included, even for clients that send once
- The builder list, and any other bundle field, is config
- Requests are signed with `X-Flashbots-Signature`, and the key is redacted wherever config is printed
- One counter for every outcome

### How it works

A project-level pre-forward hook answers `eth_sendRawTransaction` on any EVM network that
sets `evm.bundleSubmission`. It runs before the cache and before upstream selection, so the
transaction never enters the normal path. For each request it:

1. Decodes the signed transaction to get its hash, sender and nonce. A transaction is
   rejected as an invalid request, and nothing is sent anywhere, if it can't be decoded,
   has no recoverable sender, or is signed for another chain.
2. Reads the network head `N`: the highest latest block across the network's upstreams. If
   no upstream has reported a head yet, it returns a retryable error and sends nothing.
3. Builds `targetBlocks` bundles, one for each of blocks `N+1` to `N+targetBlocks`. Each
   bundle is `bundleFields`, copied verbatim, plus `txs: [<raw tx>]` and
   `blockNumber: <hex>`.
4. Forwards them concurrently as `eth_sendBundle` sub-requests, pinned to the upstreams
   matching `useUpstream` (the same selector syntax as the `use-upstream` directive).
   Sub-requests go through the network as usual, so the network's failsafe entry for
   `eth_sendBundle`, rate limits, metrics and request signing all apply.
5. Answers the caller with the transaction hash as soon as one target block is accepted.
   The remaining submissions keep running after the answer. They are bounded by the
   `eth_sendBundle` failsafe policy, with a 30s safety cap.
   - If every target block fails, the caller gets the error for the earliest target block.
6. **Keeps an accepted transaction alive.** A bundle is only valid for the block it
   targets, so eRPC stays responsible for the transaction after answering. On each new
   network head it does two things:
   - It reads the sender's on-chain nonce (`eth_getTransactionCount`, `latest`, one read
     per sender). Once the nonce passes the transaction's nonce, meaning it was included or
     replaced, eRPC stops.
   - Otherwise it submits the transaction for every target block (`head+1` to
     `head+targetBlocks`) that no relay has accepted yet and no submission is running for.
     That is normally just the block the new head brings into reach. It also covers any
     earlier target block whose submission failed, so a partial rejection is retried
     rather than left uncovered.

   This goes on for `resubmitFor` after the most recent broadcast, and a re-broadcast
   restarts the window. When the window runs out with the nonce unmoved, eRPC gives up and
   counts the transaction as `expired`, so a drop is never silent.

   Kept transactions live in memory, one set per network per process, capped at 10,000. A
   restart forgets them, as a node restart forgets its mempool.

Requests to an upstream that sets `jsonRpc.flashbotsSigningKey` carry the header
`X-Flashbots-Signature: <address>:<signature>`. The signature is the EIP-191
personal-message signature of the `0x`-prefixed hex of `keccak256(body)`. It is computed
over the exact bytes sent, which is why request gzip and batching are refused on a signing
upstream.

### Config schema

| Field | Type | Default | Notes |
|---|---|---|---|
| `networks[].evm.bundleSubmission.useUpstream` | string | — (required) | Upstream id or tag that receives the bundles. Must match only bundle relays. |
| `networks[].evm.bundleSubmission.targetBlocks` | int | `3` | Consecutive blocks per broadcast, starting at head + 1. Must be ≥ 1. |
| `networks[].evm.bundleSubmission.resubmitFor` | duration | `5m` | How long after its latest broadcast an accepted transaction keeps being submitted for each new block. Stops early once the sender's nonce passes it. Flashbots Protect keeps transactions for 25 blocks, about 5 minutes on mainnet. |
| `networks[].evm.bundleSubmission.bundleFields` | map | none | Merged verbatim into every `eth_sendBundle` params object (`builders`, `refundPercent`, …). Setting `txs` or `blockNumber` is a config error. |
| `upstreams[].jsonRpc.flashbotsSigningKey` | string (secret) | none | 32-byte hex secp256k1 key. Prints as `REDACTED` in the config log, `erpc_config` and config dumps. Requires `enableGzip` and `supportsBatch` to be off. |

`bundleSubmission` is rejected under `networkDefaults.evm`. Networks created on demand copy
`networkDefaults.evm` wholesale, so a default would route every chain's writes to the
bundle relays, including chains that have none.

### Worked examples

**Ethereum mainnet, with a dedicated write policy.** `eth_sendBundle` is idempotent for the
same transaction and block, so a retry is safe. A short timeout keeps failures inside the
caller's own submit timeout:

```yaml
networks:
  - architecture: evm
    evm:
      chainId: 1
      bundleSubmission:
        useUpstream: bundle-relay
        targetBlocks: 3
        bundleFields:
          builders: [flashbots, Titan, beaverbuild.org]
    failsafe:
      - matchMethod: eth_sendBundle
        timeout: { duration: 4s }
        retry: { maxAttempts: 2, delay: 300ms }
      - matchMethod: "*"
        timeout: { duration: 30s }
```

**Sepolia, for end-to-end testing.** Use the same shape with
`endpoint: https://relay-sepolia.flashbots.net`, `evm: { chainId: 11155111 }`, and no
`builders`.

### Request/response behavior

| Case | Caller gets | Sent |
|---|---|---|
| At least one target block accepted | `result: <tx hash>` | All `targetBlocks` bundles |
| Every target block rejected | The earliest target block's error, normalized like any upstream error | All bundles |
| Transaction undecodable, without a valid sender, or signed for another chain | Invalid-request error (HTTP 400) | Nothing |
| Network head unknown | Retryable, exhausted-class error | Nothing |
| Caller goes away first | The context error | Bundles keep going |

The existing `eth_sendRawTransaction` network post-forward check still applies to
exhausted-class errors. eRPC looks the hash up through the network, and if the transaction
is already on-chain it answers success. Only the hash is sent for that lookup, never the
transaction.

### Best practices

- Lock each relay upstream to bundle methods (`ignoreMethods: ["*"]` plus
  `allowMethods: [eth_sendBundle]`). Some relays also accept a raw `eth_sendRawTransaction`,
  with undocumented handling.
- Give `eth_sendBundle` its own failsafe entry, ahead of the catch-all.
- Keep `targetBlocks` small (2–3). Keep-alive already covers later blocks, and a large value
  only multiplies the requests each broadcast makes.
- Set `resubmitFor` to how long a transaction should wait for inclusion before being
  dropped. Alert on `erpc_bundle_keepalive_total{outcome="expired"}`.
- Use a dedicated signing key that holds no funds, one per environment, loaded from the
  environment. Flashbots tracks reputation per signing address.

### Edge cases & gotchas

1. **Only `eth_sendRawTransaction` is covered.** Other send methods take the normal path.
2. **Callers lose some mempool semantics.** A held transaction is invisible to ordinary
   upstreams, so the following no longer behave as they would with a public mempool:
   - `eth_getTransactionCount(…, "pending")` doesn't count it.
   - `eth_getTransactionByHash` returns null until it lands.
   - Relays don't report `nonce too low` or `underpriced` at submission.
   - A transaction that never lands (for example one that keeps reverting) is dropped when
     `resubmitFor` runs out, but its nonce stays unused, so later nonces from the same
     sender stay blocked.

   Clients must take nonces from their own ledger, and must replace a nonce that won't land.
3. **A relay upstream counts toward the network head and passes health gates.** If the
   selection policy excludes every ordinary upstream, the write-only relay can be the only
   survivor. Reads then fail with "method ignored" instead of the policy's outage fallback
   to the full upstream set (upstream erpc#1125).
4. **A `use-upstream` directive on the incoming request doesn't override the relay pin.**
5. **Revert protection is enforced by builders, not by the relay.** After a reorg, a
   transaction from an included bundle can re-enter the public mempool. Every listed
   builder sees your transactions.
6. **Relay errors aren't always standard JSON-RPC.** For example, Flashbots answers an
   unsigned bundle with `-32600 "signature is required"` and `"id": null`. They are
   normalized like any upstream error.
7. **Keep-alive is per process.** A client's re-broadcast may reach another rpc-proxy
   replica, which then keeps the transaction too. The resubmissions duplicate each other
   harmlessly: the same transaction for the same block.

### Observability

| Metric | Type | Labels | When it fires |
|---|---|---|---|
| `erpc_bundle_submission_total` | counter | project, network, outcome | Once per answered `eth_sendRawTransaction`. Outcome is one of: `accepted`, `rejected`, `invalid_tx`, `head_unknown`, `abandoned`. |
| `erpc_bundle_keepalive_total` | counter | project, network, outcome | Once per kept transaction when keep-alive stops. Outcome is one of: `settled` (nonce passed: included or replaced), `expired` (window ran out with the nonce unmoved: **dropped**), `overflow` (not kept, cap reached), `disabled` (bundleSubmission removed). |
| `erpc_bundle_keepalive_tracked` | gauge | project, network | Transactions currently kept alive |
| `erpc_upstream_request_total{category="eth_sendBundle"}` and the other upstream metrics | counter | standard | Every bundle sub-request, per relay upstream |
